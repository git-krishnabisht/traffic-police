A release of fixes from a check of the whole project. Attach mode no longer misses an app's first
HttpURLConnection requests on a slow device, no single response body can freeze traffic-police or
run it out of memory, the screen no longer stands still while a file is saved or the bodies are
searched, and the download is about a fifth smaller.

## Install or update

```sh
curl -fsSL https://raw.githubusercontent.com/git-krishnabisht/traffic-police/master/install.sh | sh
```

On Windows, in PowerShell:
`irm https://raw.githubusercontent.com/git-krishnabisht/traffic-police/master/install.ps1 | iex`.
The installer takes the file for your system from this page, checks it against `SHA256SUMS.txt`,
puts it in `~/.local/bin` (on Windows `%LOCALAPPDATA%\Programs\traffic-police`) and adds that
folder to your PATH; running it again updates. The README's Install section has the options.

## New

- **`TrafficPolice.buffer(requests, bytes)`** in the Android library sets what the runtime keeps
  for a traffic-police that connects later. By default that is the app's last 1,000 requests in
  at most 32 MB, kept from the start whether traffic-police connects or not. An app short of
  memory can keep less, first thing in `Application.onCreate`:
  `TrafficPolice.buffer(200, 4L * 1024 * 1024)`, or `buffer(0, 0)` to keep none. In
  `capture-noop` it does nothing.
- **A body too long to show whole shows its start.** The viewer formats the first 32 MB of a
  body once decoded, and a view holds at most 1,000,000 lines and 64 MB of text. Past that, the
  last line says what is not shown, and the detail pane says that `w` saves all of it. The hex
  view, jq and saving still have the whole body.
- Nesting is indented 32 levels at most; a deeper line shows its depth there (`40›`).

## Changed

- **The download is about a fifth smaller.** The attach agent goes into the binary compressed
  (its 3.6 MB take 1.3 MB), and the release binaries are built with whole-program optimization:
  the macOS binary is 10.8 MB instead of 13.7 MB.
- **Saving happens in the background.** A body, a HAR file or a session file is written from a
  snapshot while the screen and the capture go on, and the footer says when it is done. `:q`
  waits for a file still being written; a second `:q` stops it and removes the unfinished file.
  A file that is there already is never overwritten.
- **`body:` searches** run in the background, and start once you stop typing for a moment (Enter
  starts them at once).
- **`tail` and `record`** no longer keep every request: each one goes once it has been printed or
  written, so a day-long `tail` stays small.
- **zstd bodies** may use an 8 MB window at most, as RFC 9659 has it for HTTP. A body that asks
  for more is shown as captured, with the reason.
- **Session files** are read a piece at a time, and at most their first 4 GB once unpacked (the
  title says when a file holds more).
- **The Android library** gathers short body writes (`read()` and `write(int)` loops) into chunks
  of up to 8 KB, sent within 50 ms. What it keeps before traffic-police connects now counts what
  the requests really take (headers, stacks and frames as well as bodies), so fewer of them may
  fit in the 32 MB than before.
- **A rule set too big for the app** (over 15 MB with its bodies) is refused, with a problem that
  names the rule that takes the most room. Before, sending it crashed the capture.
- **The installers' progress bar** starts 6 processes a frame instead of about 30. The one-line
  installers come from the repository, so they have done this since 2026-10-14.

## Fixed

- **Attach mode could miss an app's first HttpURLConnection requests on a slow device**, when the
  agent loads as the app starts (`--launch`, and `--follow` across a restart on Android 11 and
  later). The agent hooked `java.net.URL` only after it had gone through every class already
  loaded; it now does so as soon as its runtime captures. OkHttp's requests were not affected.
- **One response body could freeze traffic-police or run it out of memory:**
  - deeply nested HTML or XML (255 KB of nested tags made 7 GB of text);
  - a small compressed body that decodes to hundreds of MB (it was decoded and laid out on the
    screen's thread);
  - a large session file (it was unpacked whole);
  - a large Flutter body (a 30 MB body took 4.4 GB);
  - a busy WebSocket (its messages were all kept in memory and listed again every frame).
- **The screen could stand still:**
  - for seconds while a HAR or session file of a big session was made;
  - while a `body:` filter was typed;
  - on the Overview of a small body that decodes large (27 ms a frame);
  - with a collapsed group of thousands of repeats (up to 131 ms a frame);
  - when a large body was opened;
  - while a backend's data kept coming.
- **`body:` could show the wrong rows:** a result found for an earlier keystroke (`body:ab`)
  counted for the new text (`body:abc`).
- **A crash in a background task** (a decode, a search, jq) reset the terminal and deleted the
  bodies kept on disk while traffic-police went on. The task now says it failed, and nothing else
  changes.
- **Saving a session could end traffic-police** when the device's log had many long lines (a
  record over 16 MB).
- **The Android library, in debug builds:**
  - a body read or written a byte at a time took about 100 bytes of the app's memory a byte;
  - an exception of the library's own could reach the app from HttpURLConnection's streams,
    OkHttp's request bodies and the rules. A regex `replace` whose `with` does not fit its pattern
    (`$9`), or whose pattern runs out of stack on a long body, now leaves the body alone and says
    why;
  - `body_cap_reached` was not reported when writes filled the cap exactly;
  - its writer woke up four times a second with nothing to do;
  - starting up, it read the HTTP clients' versions (which initializes gRPC) and made its instance
    id on the app's main thread, before `Application.onCreate`.
- **`doctor`** listed a config file's problems without a fix line, as every other failure has.

## Compatible with earlier versions

The protocol is still version 1: traffic-police 0.5.2 works with apps built with the 0.5.1
library, and the other way round. The Android libraries 0.5.2 have the changes above, `buffer` new
in both. The attach agent inside the binary is still 0.2.0 (its boot interface is the same), with
the 0.5.2 runtime. Session files and `config.toml` files from earlier versions keep working. The
library is in the Maven repository as 0.5.2:
`debugImplementation("io.trafficpolice:capture:0.5.2")` and
`releaseImplementation("io.trafficpolice:capture-noop:0.5.2")`.

## Downloads

| File | For |
|---|---|
| `traffic-police-macos-arm64` | macOS on Apple silicon |
| `traffic-police-linux-x86_64` | Linux on x86_64 with glibc 2.34 or newer (RHEL 9, Ubuntu 22.04, Debian 12, Fedora 35 and later) |
| `traffic-police-windows-x86_64.exe` | Windows 10 and 11 on x86_64 |

`SHA256SUMS.txt` has their checksums, `LICENSE` is the Apache License 2.0, and
`THIRD-PARTY-LICENSES.txt` lists the licenses of what the binaries contain.

You also need adb (Android SDK platform-tools), and a device or emulator with Android 8.0 (API 26)
or newer. The binaries are not code-signed. The installer takes care of that; if you download a
file yourself, make it executable (`chmod +x`) on macOS and Linux, and on macOS run
`xattr -d com.apple.quarantine traffic-police-macos-arm64`, since macOS refuses a downloaded file
from an unidentified developer. Windows may warn that the publisher is unknown.

## Known limits

- Logdawg is in the UI only: `tail` and `record` do not read the log.
- The filter does not have Studio's `is:firebase` or its match-case switch (case never matters).
- gRPC in attach mode: calls an app makes with `channel.newCall` on a channel it built before the
  attach are not seen (calls through stubs are).
- WebSockets in attach mode: a socket whose handshake ends before the app's `newWebSocket` call
  returns (only seen with a server in the same process) reaches the app's listener unwrapped, and
  what the app sends through that socket is not captured. Library mode does not have this gap.
- Flutter mode misses requests made before it connected, shows a body once its request has
  ended, and cannot apply rules.
- Not captured: Cronet, WebView, native sockets, and an OkHttp whose names a minified debug build
  changed (`doctor` shows the hooks' status).
- No build for Intel Macs or Linux on ARM yet: build from source (README).
